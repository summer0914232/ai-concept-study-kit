1一句话定义

把做某件事的成熟方法写成文件，让 AI 在需要时自己翻出来照着做。

事实在当下的工程实现里（以 Anthropic 的 Agent Skills 为代表），一个 Skill 的最小形态是一个文件夹 + 一份带 YAML 元数据的 SKILL.md；除说明文件外，还可以打包脚本、模板和参考文档，供模型按需取用。

它不是什么：

  • 不是一段保存下来的提示词。提示词是一次性的输入，Skill 是带目录、带资源、可版本管理的制品。
  • 不是给模型装新知识。它不改模型权重，也不检索知识库，注入的是做事的流程。
  • 不是自动执行的程序。它更像作业指导书，仍然由大模型来阅读和执行——除非里面附带了可运行脚本。

2我的理解

类比：餐厅墙上的 SOP 活页夹

大模型像一个聪明但刚入职、不了解本店规矩的员工。你可以每次口头交代一遍（= 写提示词），也可以把规矩写进墙上的活页夹，谁来上班自己翻（= 写 Skill）。这个活页夹设计得很讲究：

  • 封面目录只有一行字——「客户投诉怎么处理」，一眼能扫完；
  • 翻到那一页才是详细步骤；
  • 最后才是附录表格——话术模板、退款金额对照表，用得着才翻。

这三层结构不是随手设计的，它正好对应上下文这个稀缺资源：目录常驻，正文按需，附录随用随取。

这个类比在哪一步失效：人读 SOP 会理解背后的意图，写得含糊也能自行补全；模型只是"照着字做"——步骤含糊，它会跑出很自信的错误。所以给机器看的作业指导书，必须比给人看的更死板、更啰嗦、更多判据。这也是为什么我给自己写的 Skill 里会专门放一条"自检清单"。

认知修正

我原来以为 Skill 就是"把常用提示词存起来下次复用"。
查证后发现，至少有三点被我漏掉了：
① 它是文件夹，不是字符串。事实官方文档定义的 Skill 是包含 SKILL.md 及可选脚本、模板、参考文档的目录结构，而不只是一段文本。
② 它按需加载。事实官方把这种机制叫渐进式披露（progressive disclosure）：会话开始时只有 Skill 的 name 和 description 被读入上下文，判断相关后才加载正文，配套的脚本与参考文档更是只在需要时才读取——脚本甚至可以直接执行而不占用上下文。
③ 触发是模型自己判断的。description 写得准不准，直接决定该用的时候会不会被想起来。

一句可被反驳的判断

我的判断我认为 Skill 真正的价值不在"省下几句提示词"，而在于把 AI 的行为从"聊天框里的即兴发挥"变成了可版本化、可评审、可团队共享的工程制品。
理由：推断省提示词只是效率问题，而一旦方法论变成仓库里的文件，它就有了 diff、有了 review、有了迭代历史，团队里别人犯过的错可以一次性地沉淀进去、不再重犯——这一点是提示词复用做不到的。
反驳我的方式：如果只是个人偶尔做一次的任务，写规范 Skill（元数据 + 适用场景 + 流程 + 输出结构 + 自检）的成本明显高于直接说一句需求，此时"即兴发挥"更划算。所以 Skill 的适用前提是同类任务会反复出现，或需要多人共用同一套标准。

3核心机制

3.1 一个 Skill 由什么组成

组成内容什么时候被读进上下文
YAML 元数据name + description（必填），可加版本、标签等始终常驻——这是它被想起来的唯一入口
正文适用场景、输入、步骤、输出结构、来源要求、自检要求判断相关之后才加载
附带资源templates/、scripts/、references/用到才读；脚本可直接执行，不占上下文

3.2 加载机制：渐进式披露（三层）

flowchart LR subgraph L1["第 1 层 · 常驻上下文"] A["name + description
（每个 Skill 只占几十个 token）"] end subgraph L2["第 2 层 · 命中才加载"] B["SKILL.md 正文
适用场景 / 步骤 / 输出结构 / 自检"] end subgraph L3["第 3 层 · 用到才读取"] C["references/ 参考文档"] D["templates/ 模板"] E["scripts/ 脚本 → 直接执行，不进上下文"] end Q["用户请求"] --> A A -- "描述匹配 → 触发" --> B B -- "需要细节时" --> C B -- "需要格式时" --> D B -- "需要确定性动作时" --> E
文字版兜底：第一层，所有 Skill 的名称与描述常驻模型上下文，成本极低，作用是"让模型知道有这门手艺"；第二层，模型判断当前任务与某条描述匹配，才把该 Skill 的正文读进来；第三层，正文里若指向参考文档、模板或脚本，则在执行过程中按需读取——脚本直接运行，连上下文都不占。整个设计的目的只有一个：在有限的上下文里塞进尽可能多的可用能力。

3.3 关键变量

变量为什么它决定成败
description 的写法写太窄 → 该用时想不起来；写太宽 → 无关任务被误触发。事实官方工具写作指南同样强调：描述要写清"什么时候该用、什么时候不该用"
粒度一个 Skill 只做一类事。把三件事塞进一个 Skill，等于三个都触发不准
正文长度正文一旦被加载就真金白银地占上下文；细节应下沉到 references/
是否附带可执行脚本确定性动作交给脚本，比让模型每次现场写代码更稳、更省、更可复现
是否写自检清单我的判断这是我认为最容易被忽略、但对质量下限影响最大的一项——没有自检的 Skill，输出质量完全取决于模型当天状态

4一个具体应用场景

每周把一篇论文 PDF 整理成固定格式的中文笔记

  • 不写 Skill 的做法：每周在对话框里重新交代一遍——"要中文、要八节结构、来源必须可访问、要有我自己的理解"。结果是每周格式都在飘，而且一旦漏说一条要求，那周的笔记就缺一块。
  • 写成 Skill 的做法：建 .workbuddy/skills/paper-note/SKILL.md，把输入（PDF 路径）、步骤（抽结构 → 提炼 → 按模板输出 → 自检来源）、输出（固定八节）、自检（外链必须当日验活）全部写死，并把排版模板放进 templates/。
  • 输入：一篇新 PDF 的路径。
  • 过程：模型看到"整理论文笔记"的请求 → 匹配到 paper-note 的描述 → 加载正文 → 按步骤执行 → 套用模板输出。
  • 输出：与上周格式完全一致的笔记 + 来源核验表。
  • 失败会怎样：三种典型的失败——
失败模式表现根因
该触发没触发模型完全没想起有这个 Skill，自己自由发挥description 写得太窄，没覆盖用户实际会用的问法
触发了但不照做读了正文，输出却还是老样子步骤写成了"要注意格式要规范"这类抽象要求，缺少可判定的具体动作
静默过时某天开始莫名失败Skill 依赖的外部工具/接口变了，而文件还停留在旧版本
这个场景最值得记的一句：Skill 沉淀的是流程，不是结果。它保证的是"每次都按同一套可靠步骤走"，而不是"每次都能得到正确答案"——后者还得靠自检清单兜底。

5容易混淆的问题与使用边界

5.1 易混淆对照

混淆对区别判别法
Skill vs 提示词提示词是一次性的输入；Skill 是带目录结构、可版本管理、按需加载的制品问：它有 diff 吗？能 git 提交、能让同学 clone 下来用吗？
Skill vs 工具 / MCP事实MCP 解决的是"能连上什么"（数据与服务的连接协议）；Skill 解决的是"拿到能力后该怎么干"把 Skill 删掉，工具照样能连；把 MCP 删掉，Skill 里的步骤无处施展
Skill vs 微调 / RAG微调改权重、RAG 检索知识；Skill 都不做，它注入的是程序性知识（怎么做）问：它教的是"知道什么"还是"怎么一步步做"？
Skill vs 记忆Skill 是人主动写、稳定不变的方法论；记忆是系统自动积累、会随交互变化的事实问：这条内容改一次要发版吗？要的＝Skill
Skill vs WorkflowWorkflow 是执行路径本身；Skill 是被路径调用的"能力包"Workflow 说"先 A 后 B"，Skill 说"A 这件事怎么做"

「程序性知识（knowledge-how）」这一哲学区分，可参见《斯坦福哲学百科》"Knowledge-how" 条目——它把"知道怎么做"与"知道某事实"明确分开，正好对应 Skill 与 RAG 的分工。

5.2 使用边界（什么时候不该写 Skill）

  1. 只做一次的任务。写规范 Skill 的成本高于直接提需求。
  2. 指望它补领域知识。Skill 教流程，不教事实；事实要来自可核查来源（见 上下文 一页）。
  3. 依赖外部工具却无人维护。接口一变，Skill 就静默失效，而且失效时往往不报错。
  4. 把密钥、个人隐私写进 Skill。它会被提交进仓库、被读进上下文—— Skills 里只能放方法，不能放凭据。
  5. 把它当成质量保证。Skill 保证的是过程一致；要兜住输出质量，得靠 Skill 内部那条自检清单。

6最小实践（15 分钟）

亲手建一个最小可用 Skill，并测它的触发

# 1. 建目录（项目级 Skill 的位置）
mkdir -p .workbuddy/skills/my-first-skill

# 2. 写最小骨架（把下面内容存成 SKILL.md）
cat > .workbuddy/skills/my-first-skill/SKILL.md <<'EOF'
---
name: my-first-skill
description: 把一段长文本压缩成 5 条要点。当用户说「总结一下」「提炼要点」「太长了我只看重点」时使用。不适合需要保留精确数字的场合。
---

# 我的第一个 Skill

## 适用场景
用户给了长文本，想要 5 条以内的要点。

## 输入
- text：待压缩的长文本（必填）
- language：输出语言（默认中文）

## 步骤
1. 通读全文，标出 3-5 个信息密度最高的句子
2. 每条要点不超过 30 字，写成完整句子
3. 检查：5 条里有没有两条在说同一件事？有就合并

## 输出结构
1. 一句话总括
2. 五条要点（编号列表）
3. 被舍弃的信息类型（一句话说明丢了什么）

## 自检
- [ ] 要点 ≤5 条，每条 ≤30 字
- [ ] 没有两条重复
- [ ] 明确写出了"丢了什么"
EOF

然后做触发实验（这一步才是关键）

用三种不同的说法去问同一个需求，看它会不会自动被想起来：

  1. 「帮我总结一下这段话」→ 预期：触发
  2. 「这段话太长了，我只想知道重点」→ 预期：触发
  3. 「这段话一共有多少个字？」→ 预期：不触发（如果也触发了，说明 description 写太宽）
做完这个实验你会明白：Skill 里最难写、也最重要的两行，是 YAML 里的 name 和 description——其余内容写得再好，触发不了就等于不存在。
