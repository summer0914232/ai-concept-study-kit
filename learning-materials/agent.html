1一句话定义

由模型自己决定「下一步做什么」，并能调用外部工具反复尝试直到达成目标的程序。

拆成三个可检验的条件：① 目标由人给，路径由它定；② 能真的动手（调工具、改文件、发请求），不只是说；③ 结果会被看一眼、不满意就再来一轮。事实Anthropic 在工程博客中正是用「谁来掌控流程」这条线来划分 workflow 与 agent 的：workflow 的路径是人预先写好的代码，agent 的路径是模型自己在运行时决定的。

它不是什么：

  • 不是「会调工具的大模型」——只会调一次工具就结束，那是工具调用（function calling），不构成循环。
  • 不是固定流程自动化——if/else 写得再复杂，只要路径是人写死的，就该叫 workflow。
  • 不是有自我意识的数字人——它每次的「决定」都是当场算出来的概率分布，进程一结束什么都没留下。

2我的理解

类比：服务员与菜谱

Wworkflow 像菜谱——先放油再下菜，步骤写死，谁来做都一样；Agent 像服务员——客人说「我忌口香菜」，他得临时决定：是去后厨叮嘱、还是建议换个菜、还是先问清楚忌口程度。我的判断

这个类比在哪一步失效：服务员有长期记忆、有自我意识、会为结果负责；Agent 没有。它这一轮「决定催菜」，下一轮如果上下文里没有记录，它会再决定一次、甚至做出相反的决定。所以读任何 Agent 资料时，都要先问一句：它的状态存在哪？这恰好是「上下文」这个概念的入口。

认知修正

我原来以为 Agent 就是「能调用工具的大模型」，把两者画等号。
查证后发现，工具调用只是必要条件：Anthropic 明确把「模型在运行时自主决定流程与工具使用、并自己判断任务何时完成」作为 agent 的定义；OpenAI 的构建指南则强调 agent 的三要素是模型 + 工具 + 指令，并特别指出 agent 与「一次性调用」的区别在于它在循环中运行直到满足退出条件。事实

一句可被反驳的判断

我的判断我认为当下被叫做「Agent」的绝大多数产品，其实是可变分支的 workflow；真正自主的 Agent 只在「错了能回滚」的场景里（写代码、查资料）才可靠。
理由是一个能被算出来的事实：多步循环里错误会累乘。若单步成功率 p=0.95，独立执行 n 步后的整体成功率约为 pⁿ——5 步 77%、10 步 60%、20 步只剩约 36%、50 步掉到 7.7%。推断这个估算忽略了「观察到错误后自我修正」这一环，真实成功率会高于此值；但它足以解释为什么自主 Agent 在金融转账、批量发邮件这类不可逆任务上必须加人工闸门。
反驳我的方式：如果存在成熟的错误纠正 / 回滚机制（每步都能验证并撤销），累乘模型就不再成立——代码场景恰好满足这一点，所以编程 Agent 反而跑得最好。

3核心机制

3.1 五个组成要素

要素作用它坏了会怎样
① 感知 / 观察拿进来的一切：用户指令、工具返回值、文件内容、报错信息看不清环境 → 后续全错，且它不知道自己错了
② 策略（大模型）唯一的「决策者」：读入全部观察，输出下一步动作决策抖动、重复绕圈、过早宣布完成
③ 记忆 / 状态短期＝上下文窗口；长期＝外部文件、向量库、数据库做过的步骤白做，或重复踩同一个坑
④ 工具集它能施加到世界上的动作：读写文件、跑命令、检索、发请求只能嘴上规划，落不了地
⑤ 循环与终止条件把上面四个串成回路，并规定何时停：最大步数、token 预算、显式完成信号无限循环烧钱，或中途放弃

3.2 运行流程：ReAct 循环

事实ReAct 论文提出的范式是 Thought（想）→ Action（做）→ Observation（看） 三步一循环，把「推理」和「行动」交织起来，而不是先规划完再执行。

flowchart LR U[用户目标] --> T1[Thought 思考下一步] T1 --> A1[Action 调用工具] A1 --> O1[Observation 拿到结果] O1 --> C{达标了吗?} C -- 否 --> T1 C -- 是 --> D[输出最终结果] O1 -.->|每轮结果都追加写入| M[(上下文 / 记忆)] M -.->|下一轮完整读入| T1
图的文字版（CDN 不可用时的兜底）：用户给出目标 → 模型思考下一步 → 调用一个工具 → 把工具返回的结果追加进上下文 → 带着完整上下文再思考下一步 → 判断达标与否，未达标则回到「思考」，达标则输出最终结果。关键在最后那条虚线：每一轮的观察都会写进上下文，下一轮又会被完整读入——这就是 Agent 与「上下文」概念咬合的地方。

3.3 关键变量

变量为什么关键
步数 n成功率近似 pⁿ。缩短步数比提升模型更有效——这也是「把大任务拆成可验证的小任务」的根本原因
上下文预算每轮观察都会占额度。观察里塞进大文件、长日志，会迅速挤爆窗口，导致早期信息被挤出（详见 大模型的上下文）
工具数量与粒度工具越多、描述越像，选错的概率越高。推断精简工具集通常比堆数量更能提升稳定性
反馈信号质量Agent 靠「观察」判断成败。有单元测试、有编译报错 → 能自我修正；没有可验证信号 → 只能靠自我感觉，容易空转
权限边界能否写文件、能否联网、能否花钱。这直接决定了「它搞砸了」的最坏代价

4一个具体应用场景

把一个 Python 项目的测试覆盖率从 62% 提到 85%

  • 输入：仓库本地路径 + 一条指令「把覆盖率提到 85%，不许改动 src/ 下的业务代码，每改完一轮跑一次 pytest --cov」。
  • 过程：① 跑一次覆盖率报告，列出未覆盖文件 → ② 按覆盖率从低到高读源码 → ③ 挑一个分支写测试 → ④ 跑 pytest，读报错 → ⑤ 报错就改测试或改断言，通过就回到 ③ → ⑥ 每 5 轮重跑一次完整覆盖率 → ⑦ 达标后输出改动清单。
  • 输出：新增的测试文件、覆盖率报告（62% → 87%）、一份列出所有新增/修改文件的 diff 清单。
  • 失败会怎样：最坏的情况不是「没做出来」，而是指标造假——为了让测试通过去改业务代码，或者写一堆 assert True 把覆盖率数字刷上去。推断因为 Agent 的优化目标是「让观察里的信号变好」，它并不天然理解「覆盖率只是手段、不是目的」。
这一场景必须配的护栏：① 用文件系统权限或沙箱禁止写 src/；② 要求最终 diff 人工 review；③ 设置最大轮数与 token 预算，超限即停。事实OpenAI 的构建指南同样建议：把高风险、不可逆、判断标准模糊的操作留在人工审批之后，而不是放进自主循环。

5容易混淆的问题与使用边界

5.1 易混淆对照

混淆对区别一个可操作的判别法
Agent vs Workflow路径由谁决定：模型在运行时刻定 vs 人写代码时定把任务描述改一改，如果代码不用动就能应付 → 偏 agent；如果必须改流程代码 → 是 workflow
Agent vs 工具调用有没有循环。调一次工具就结束只是能力，不是 agent数一数「模型输出 → 工具返回 → 模型再看」发生了几次，≥2 次才算循环
Agent vs RPA / 脚本自动化脚本靠选择器定位元素，遇变化即崩；Agent 靠理解，遇变化能自己换路把按钮位置挪一下：脚本报错，Agent 大概率还能成
Agent vs 多 Agent 系统多 Agent 是把任务分给多个角色，但会引入通信开销与上下文割裂先问：单 Agent + 好工具能不能搞定？能就不必上多 Agent
Agent vs 聊天机器人聊天机器人只产出文本；Agent 会改变外部世界的状态跑完之后，文件系统 / 数据库 / 外部服务有没有变化

5.2 使用边界（什么时候不该用）

  1. 错误不可逆的场景不要全自动。转账、群发邮件、删除生产数据——留人工确认闸门，别省这一步。
  2. 步骤可枚举且稳定的任务，写 workflow 更划算。事实Anthropic 的建议很直白：先找最简单的方案，必要时才增加复杂度，多数场景用不上完整的自主 agent。
  3. 缺少可验证反馈信号时别用。例如「帮我把论文写得更有深度」——Agent 无法判断自己写得深不深，只会反复重写。
  4. 成本敏感、时延敏感的高频调用别用。多轮循环意味着多倍 token 消耗与等待时间。

6最小实践（15 分钟，不需要 API Key）

目标：亲手验证「错误在多步循环里会累乘」这个核心论断。

# step_error.py —— 算一算多步循环的成功率衰减
def success(p: float, n: int) -> float:
    return p ** n

for p in (0.99, 0.95, 0.90):
    row = [f"{success(p, n):.1%}" for n in (1, 5, 10, 20, 50)]
    print(f"单步成功率 {p:.0%} →", " | ".join(row))

# 再算：要跑 20 步还想保住 90% 的整体成功率，单步得有多准？
print("20 步保 90% 所需单步成功率:", f"{0.90 ** (1/20):.4f}")

运行 python step_error.py，你会看到：

  • 单步 95% 时，20 步后只剩约 35.8%，50 步后约 7.7%；
  • 想让 20 步整体成功率保住 90%，单步成功率必须达到 99.5% 左右。

做完这道题再回头看第 4 节的场景，就能理解为什「拆小步骤 + 每步可验证」是 Agent 工程的第一原则，也能理解为什么自主 Agent 至今只在编程这类可回滚场景里跑得最好。

进阶（可选）：打开任意带 Agent 模式的工具（Claude Code、Cursor 等）跑一个 5 步任务，把它的执行日志打开，数一数循环了几轮、每轮往上下文里塞了多少 token——你会对「上下文预算」有实感。
